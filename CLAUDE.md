# OnlyBudget — notes for future sessions

Read README.md first. The five product principles there are non-negotiable and every change must respect them: no bank linking, voice and text equal, no dark patterns, local-first with backup, calm not gamified.

- Pure logic (parser, plain-language sentences, recurring schedule, export, crypto) lives in `src/parser` and `src/lib` and must stay free of React Native imports so `npm test` covers it.
- The parser never saves anything on its own. Every path ends at `ConfirmationCard`.
- Copy in the UI is plain sentences. No "over budget!", no red states, no streaks.
- Every user-facing string comes from `useT()` / the locale tables in `src/i18n/locales`. Adding a key means adding it to all eight locale files (the `LocaleDef` type enforces it). Parser behavior per language lives in `src/parser/packs`.
- Schema changes go in a new entry of `MIGRATIONS` in `src/db/database.ts`. Never edit an existing migration.
- Budget periods: the Today and Budget screens show one `Period` (`{start, end}`), the calendar month by default or payday-to-payday when `settings.budgetPeriod` is `pay`. Paydays come only from active repeating income rules (`src/lib/periods.ts`); with none, pay mode falls back to the month. Category limits, the optional overall plan (`settings.overallLimit`) and roll-over all apply per period. Roll-over (`category.rollover`: reset, carry, ask) is computed in `src/lib/rollover.ts` from earlier periods on or after `rolloverSince`; only unspent money carries, never a shortfall; "ask" answers live in the `carryovers` table keyed by period start. Removing an entry never shows a dialog: the `UndoBar` on the tabs puts it back (`lastDeleted` in the store).
- Parser kinds: transaction, goal (kind saving or debt), contribution, reminder, question. Reminder phrasing per language lives in the `reminder` block of each pack (lead words, clock times, repeat words, future days); shared helpers are in `src/parser/reminderRules.ts`. Notifications are scheduled only from `src/lib/reminders.ts`, and anything that saves a reminder must handle the permission being refused (tell the user, keep the reminder).
- Questions ("how much have I spent this week on Starbucks?") are parsed by `src/parser/questionRules.ts` using the `question` block of each pack (lead words, income lead words, period words, leftovers to strip). A question is never saved: `src/lib/questions.ts` works out the range (weeks start on Sunday) and total, the sentence comes from `answerTotal`/`answerNone` in the locale, and `src/lib/speak.ts` reads it aloud with the phone's own voices when the `answerMode` setting says so (`auto` = aloud only when asked by voice). Matching a place or thing is a plain substring test; never build a RegExp from the target.
- The web build must keep working: `npm run build:web` (Metro config adds the SQLite wasm asset; nginx/dev server send COOP/COEP headers). Use `confirmDialog`/`notify` from `src/lib/dialogs.ts` instead of `Alert`, which is a no-op on web.
- Statement import: parsing is pure and lives in `src/statements` (rows → dates/money → lines → months; credit reports → tradelines; pay-off planner). PDF text extraction is the only platform-specific part (`src/components/PdfExtractor.tsx` runs pdf.js in a no-network WebView built by `scripts/build-pdf-extractor.js`; `.web.tsx` uses pdfjs-dist with the worker copied to `public/`). Never send a statement anywhere. Merchant vocabulary for statements is `STATEMENT_MERCHANTS` in `src/statements/merchants.ts`.
- Security rules (see docs/SECURITY.md): anything that crosses a trust boundary (user text, imported files, model replies) goes through `src/lib/validate.ts`; SQL is always parameterised; never build a RegExp from user data; no new outbound hosts; the web page has no inline scripts (CSP). `__tests__/security.test.ts` enforces these, and `npm run check:web-security` loads the web build under the real headers in headless Chromium.
- Voices (`settings.voice`: plain, friend, coach, roaster; `settings.attitude`: nice, playful, spicy) add one line after a save, chosen by the pure engine in `src/lib/personas` from English templates in `lines.en.ts` (other app languages get nothing until their lines exist): eight generic lines per voice, situation and attitude, plus flavour lines for coffee, restaurants, delivery, shopping, subscriptions and entertainment (`flavorFor` reads the note and category; a flavour line gets what is left appended when the category has a plan). The last 24 line keys are kept in the `app_state` table so nothing repeats soon, even across launches. Hard rules live in the engine and its tests: plain says nothing; necessities (`PROTECTED_CATEGORIES` plus a name check for custom categories) never get a line; nothing is said past a category plan or the overall plan; amounts at or above `BIG_AMOUNT` are always nice; only `TEASABLE_CATEGORIES` may be spicy. Lines target the latte, never the person. The card passes the line to the Today toast, which reads it aloud under the same rule as answers to questions. Onboarding asks once whether the user wants a voice (`VoicePicker` is shared with Settings → Voice); tapping the line on the toast opens that screen. Spoken switching ("switch to the coach", "female voice", "plain voice") is the parser kind `command` from `src/parser/commandRules.ts` (English only): applied at once in `useEntryFlow`, never saved, answered with the voice's greeting. The spoken voice's gender (`settings.voiceGender`) is picked from the phone's own voices by name in `src/lib/voices.ts`; `speak()` takes it as its third argument.
- Screens show numbers and key words, not sentences; the sentences in `locale.sentences` are for the voice (spoken answers, greetings) and for tests. `PeriodCard` (Today and Budget) is one big number that answers "what is left?" (plan remaining, else income minus spending and bills still due until the period ends, else spending), one line of in and out, the spending bar and a short label; category rows use `planShort`/`pastPlanShort`/`carriedShort`, goals use `goalShort` plus a pace word. Today also shows one spending bar (`SpendBar`: the biggest categories as segments of one hue, darkest first, 2px gaps, names underneath; colour follows size, identity comes from the labels), a "safe to spend until payday" line (`src/lib/safeToSpend.ts`: income minus spending minus repeating bills still due in the period; only with income in the period), and on Sunday and Monday a recap of last week (`src/lib/recap.ts`, weeks start Sunday; `recap` in the store). Headline sentences use Fraunces (loaded in the root layout, system face if it fails); totals count up and progress bars settle via `src/components/motion.tsx`, which honours reduced motion. `settings.accent` picks the hue family (`ACCENTS` in the theme); everything derives from it.
- Each expense category has a `tier` (`needs`, `obligations`, `comforts`, `wants`; `obligations` is shown as "Debts", since the stored id never changes but the label is a locale string), kept in `src/lib/tiers.ts` with `tierTotals`/`flexibleTotal` and migration v13. Defaults are derived so nobody configures anything: the known categories are placed by id, a custom category whose name matches `NECESSITY_WORDS` starts on `needs`, everything else starts on `comforts`, and spending with no category counts as a comfort. Savings is a `need`, so paying yourself is never shown as the leftover. The Budget screen shows the four totals with a bar each and one line adding comforts and wants; it states the split and never advises cutting anything; the only place a question is asked is `tierHint`, read while sorting a category, never beside a total. `tierOf` falls back to the default whenever the stored value is missing or unknown, so an old backup restores fine. Pay-yourself-first needs no extra code: a repeating savings transfer is an expense rule, so `safeToSpend` already subtracts it before offering anything as spendable.
- The app ships empty. Sample data lives only in `scripts/lib/shots.mjs` (shared by the `ui:scenario`, `ui:persona` and `ui:sweep` screenshot scripts) and reaches a browser session through the backup restore screen; `__tests__/release.test.ts` checks that app code never imports the scripts, carries no scenario markers, and that migrations insert only categories and settings. In-app instructions are the Help screen (`app/settings/help.tsx`, strings `helpIntro`/`helpTopics` in every locale); update a topic when its feature changes.
- Run `npm test` and `npm run typecheck` before committing. `npx expo export --platform android` is a good smoke test for bundling.
