# OnlyBudget — notes for future sessions

Read README.md first. The five product principles there are non-negotiable and every change must respect them: no bank linking, voice and text equal, no dark patterns, local-first with backup, calm not gamified.

- Pure logic (parser, plain-language sentences, recurring schedule, export, crypto) lives in `src/parser` and `src/lib` and must stay free of React Native imports so `npm test` covers it.
- The parser never saves anything on its own. Every path ends at `ConfirmationCard`.
- Copy in the UI is plain sentences. No "over budget!", no red states, no streaks.
- Every user-facing string comes from `useT()` / the locale tables in `src/i18n/locales`. Adding a key means adding it to all eight locale files (the `LocaleDef` type enforces it). Parser behavior per language lives in `src/parser/packs`.
- Schema changes go in a new entry of `MIGRATIONS` in `src/db/database.ts`. Never edit an existing migration.
- Budget periods: the Today and Budget screens show one `Period` (`{start, end}`), the calendar month by default or payday-to-payday when `settings.budgetPeriod` is `pay`. Paydays come only from active repeating income rules (`src/lib/periods.ts`); with none, pay mode falls back to the month. Category limits, the optional overall plan (`settings.overallLimit`) and roll-over all apply per period. Roll-over (`category.rollover`: reset, carry, ask) is computed in `src/lib/rollover.ts` from earlier periods on or after `rolloverSince`; only unspent money carries, never a shortfall; "ask" answers live in the `carryovers` table keyed by period start. Removing an entry never shows a dialog: the `UndoBar` on the tabs puts it back (`lastDeleted` in the store).
- Parser kinds: transaction, goal (kind saving or debt), contribution, reminder, question. Reminder phrasing per language lives in the `reminder` block of each pack (lead words, clock times, repeat words, future days); shared helpers are in `src/parser/reminderRules.ts`. Notifications are scheduled only from `src/lib/reminders.ts`, and anything that saves a reminder must handle the permission being refused (tell the user, keep the reminder).
- Questions ("how much have I spent this week on Starbucks?") are parsed by `src/parser/questionRules.ts` using the `question` block of each pack (lead words, income lead words, period words, leftovers to strip). A question is never saved: `src/lib/questions.ts` works out the range (weeks start on Sunday) and total, the sentence comes from `answerTotal`/`answerNone` in the locale, and `src/lib/speak.ts` reads it aloud with the phone's own voices when the `answerMode` setting says so (`auto` = aloud only when asked by voice). Matching a place or thing is a plain substring test; never build a RegExp from the target.
- The web build must keep working: `npm run build:web` (Metro config adds the SQLite wasm asset; nginx/dev server send COOP/COEP headers). Use `confirmDialog`/`notify` from `src/lib/dialogs.ts` instead of `Alert`, which is a no-op on web.
- Statement import: parsing is pure and lives in `src/statements` (rows → dates/money → lines → months; credit reports → tradelines; pay-off planner). PDF text extraction is the only platform-specific part (`src/components/PdfExtractor.tsx` runs pdf.js in a no-network WebView built by `scripts/build-pdf-extractor.js`; `.web.tsx` uses pdfjs-dist with the worker copied to `public/`). Never send a statement anywhere. Merchant vocabulary for statements is `STATEMENT_MERCHANTS` in `src/statements/merchants.ts`.
- Security rules (see docs/SECURITY.md): anything that crosses a trust boundary (user text, imported files, model replies) goes through `src/lib/validate.ts`; SQL is always parameterised; never build a RegExp from user data; no new outbound hosts; the web page has no inline scripts (CSP). `__tests__/security.test.ts` enforces these, and `npm run check:web-security` loads the web build under the real headers in headless Chromium.
- Voices (`settings.voice`: plain, friend, coach, roaster; `settings.attitude`: nice, playful, spicy) add one line after a save, chosen by the pure engine in `src/lib/personas` from English templates in `lines.en.ts` (other app languages get nothing until their lines exist). Hard rules live in the engine and its tests: plain says nothing; necessities (`PROTECTED_CATEGORIES` plus a name check for custom categories) never get a line; nothing is said past a category plan or the overall plan; amounts at or above `BIG_AMOUNT` are always nice; only `TEASABLE_CATEGORIES` may be spicy. Lines target the latte, never the person. The card passes the line to the Today toast, which reads it aloud under the same rule as answers to questions.
- The app ships empty. Sample data lives only in `scripts/ui-scenario-shots.mjs` and reaches a browser session through the backup restore screen; `__tests__/release.test.ts` checks that app code never imports the scripts, carries no scenario markers, and that migrations insert only categories and settings. In-app instructions are the Help screen (`app/settings/help.tsx`, strings `helpIntro`/`helpTopics` in every locale); update a topic when its feature changes.
- Run `npm test` and `npm run typecheck` before committing. `npx expo export --platform android` is a good smoke test for bundling.
